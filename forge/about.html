Build it together.

Software has an old rule: good, quick, cheap. Pick two. FORGE starts from a different question: what changes when the people building the thing can stay close to the work?

The idea

The old rule is incomplete.

Good, quick, and cheap really can pull against one another. But shorter feedback loops, shared understanding, and fewer handoffs can move all three in the right direction.

Building together does not make the tradeoffs disappear. It helps move them in the right direction.

Getting started

From conversation to working app

FORGE Code works with supported web LLM interfaces rather than one particular model. The interface may vary; the workflow stays simple.

2
Build with an LLM
Ask, apply, inspect, and repeat
2
Open a supported LLM and launch FORGE Code
Start with a normal coding request. FORGE Code supplies the protocol the model uses to work with the browser-side project.
3
Apply the model's steps
FORGE Code parses the response, shows what will change, and applies the operations to its virtual file system. You stay in the loop.
4
Open the project in FORGE IDE
Move into the IDE when you want a fuller file browser, editor, preview, diagnostics, sharing tools, or repository workflows.
3
Share or move the project
Choose the boundary that fits the work
5
Share from the IDE
A Long Link keeps the compressed project in the URL fragment. Server-backed sharing creates a compact link. Where enabled, Managed or Named Shares can provide a stable address that can be updated later.
6
Move local when you need to
FORGE CLI converts between a local directory and the same FORGE JSON used by the browser tools. Git integrations can take the project farther.
📥 Browser → local
Export or copy the project, then use forge in from the separate FORGE CLI project.
📤 Local → browser
Use forge out, then paste the project into FORGE IDE or FORGE Code.
